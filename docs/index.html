Internship Task 2

Project Overview & Objectives

Task 2 delivers the backend foundation for DevFlow: a modular RESTful engine adhering to standard HTTP semantics and enterprise conventions.

👥

User Management

List team members, query user profiles by ID, and register new members with unique normalized email enforcement and role constraints (developer, manager, designer, tester).

📁

Project Directory

Track team projects with completion progress, status flags, and relational owner assignment ensuring the referenced project owner is a valid user.

📋

Task Lifecycle Engine

Complete CRUD operations for project tasks, relational verification (projectId and assignedTo), full metadata updates, and dedicated state transitions.

🔍

Query Parameter Filtering

Filter task collections dynamically with ?status=, ?priority=, and ?projectId=, with support for combined criteria and strict enum validation.

🛡️

Strict Input Validation

Powered by express-validator. Every payload is sanitized and verified prior to reaching controller logic, returning descriptive field-level error messages.

⚙️

Centralized Error Handling

Standardized JSON response envelope across all endpoints. Includes 404 fallback routing and a global error handling middleware trapping uncaught server exceptions.

Runtime: Node.js (v24.x)
Framework: Express.js (v4.21.2)
Validation: express-validator (v7.2.1)
CORS: Enabled
Config: dotenv (v16.4.7)
Identifiers: UUID (v11.1.0)
Testing: Node Native Test Runner + Supertest
API Reference

Documented Endpoints

All API resource routes are prefixed with /api and return standard structured JSON envelopes.

Method Endpoint Description Status Codes
GET / API Welcome & Base Metadata 200 OK
GET /api/health Server Health Check & Environment Status 200 OK
GET /api/users List all registered users 200 OK
GET /api/users/:id Retrieve a single user profile by UUID 200 OK, 404 Not Found
POST /api/users Create a user with unique email validation 201 Created, 400 Bad Request, 409 Conflict
GET /api/projects List all active projects 200 OK
GET /api/projects/:id Retrieve project details by UUID 200 OK, 404 Not Found
POST /api/projects Create project (verifies owner user exists) 201 Created, 400 Bad Request, 404 Not Found
GET /api/tasks List tasks (supports query filtering) 200 OK, 400 Bad Request
GET /api/tasks/:id Retrieve task details by UUID 200 OK, 404 Not Found
POST /api/tasks Create task (verifies project & assignee exist) 201 Created, 400 Bad Request, 404 Not Found
PUT /api/tasks/:id Update task details (title, description, priority, date) 200 OK, 400 Bad Request, 404 Not Found
PATCH /api/tasks/:id/status Transition task status (todo, in-progress, done) 200 OK, 400 Bad Request, 404 Not Found
DELETE /api/tasks/:id Delete a task by UUID 200 OK, 404 Not Found
🔎

Query Parameter Filtering on GET /api/tasks

• Filter by status: GET /api/tasks?status=done (values: todo, in-progress, done)
• Filter by priority: GET /api/tasks?priority=high (values: low, medium, high)
• Filter by project: GET /api/tasks?projectId=<uuid>
• Combined filters: GET /api/tasks?status=todo&priority=low

System Design

Decoupled Layered Architecture

Organized into distinct layers separating transport concerns, validation, business domain logic, and data abstraction.

1
HTTP Entry & Middleware Layer (src/app.js & src/server.js)

Configures Express, enables CORS, parses incoming JSON payloads, and attaches route dispatchers.

2
Validation Layer (src/validators/)

Uses express-validator to reject malformed parameters or bodies with 400 Bad Request before controller execution.

3
Controller Layer (src/controllers/)

Applies domain business logic, verifies foreign entity references (e.g. project owner, task assignee), and triggers store methods.

4
Data Store Layer (src/data/store.js)

Encapsulates in-memory collections and seed data with synchronous/asynchronous interfaces, designed for seamless replacement with a persistent database in Task 3.

5
Standard Response Envelope (src/utils/response.js)

Formats every output into a uniform JSON response structure ({ success, message, data/errors }).

API Testing Toolkit

Postman Collection Included

A complete exported Postman collection is included directly inside the repository at postman/DevFlow-API.postman_collection.json.

Included Test Scenarios in Postman:

The collection includes pre-configured collection variables (baseUrl, sampleUserId, sampleProjectId, sampleTaskId) covering:

  • Root welcome and health check endpoints.
  • User listing, ID lookup, successful creation, validation errors (400), and duplicate email conflict (409).
  • Project listing, ID lookup, successful creation, and non-existent owner lookup (404).
  • Task listing, query filtering (?status, ?priority, ?projectId), task creation, full updates (PUT), status patches (PATCH), deletion (DELETE), and foreign key checks (404).
  • Catch-all 404 route handling.

Looking Ahead: Task 3 Persistent Database Integration

"Task 2 uses an in-memory data store. Persistent database integration is planned for Task 3." Because the controller layer interacts strictly with store helper abstractions, migrating to MongoDB, PostgreSQL, or MySQL in Task 3 will require zero changes to the client-facing API endpoints, HTTP contracts, or response structures.
